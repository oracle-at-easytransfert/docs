La section Réponses décrit la structure standard des réponses de l'API EASYTRANSFERT BUSINESS v1. Toutes les réponses sont en JSON et suivent un format uniforme pour simplifier le traitement côté client.

## Structure générale de la réponse

Toutes les réponses contiennent généralement ces champs :

```json
{
    "status": "success|error",
    "message": "Message descriptif",
    "data": { ... }
}
```

| Champ | Type | Description |
|-------|------|-------------|
| `status` | String | "success" si l'opération a été traitée correctement, "error" si elle a échoué |
| `message` | String | Description textuelle de l'état ou de l'erreur |
| `data` | Object | Contient les informations spécifiques à la requête (ex: transaction ID, montant, état) |

## Réponse d'une transaction /airtime

### Exemple – succès (réponse immédiate)

```json
{
    "status": "success",
    "message": "Transaction initiée avec succès",
    "data": {
        "transaction_id": "EFB.144358",
        "amount": 1000,
        "destination": "0500156008",
        "state": "PENDING",
        "custom_data": "custom_data"
    }
}
```

### Explication des champs data

| Champ | Type | Description |
|-------|------|-------------|
| `transaction_id` | String | Identifiant unique de la transaction, à utiliser pour le suivi |
| `amount` | Integer | Montant de la transaction en FCFA |
| `destination` | String | Numéro du bénéficiaire |
| `state` | String | État actuel de la transaction (PENDING, SUCCESS, FAILED) |
| `custom_data` | String | Données personnalisées passées lors de l'initiation |

<Warning>
  La confirmation finale arrive via IPN. L'état initial PENDING signifie que la transaction est en cours de traitement.
</Warning>

## Réponse d'un suivi /status

### Exemple – transaction réussie

```json
{
    "status": "success",
    "message": "Transaction réussie",
    "data": {
        "transaction_id": "EFB.144358",
        "state": "SUCCESS",
        "reponse": "operation succes",
        "error": "",
        "amount": 1000,
        "custom_data": "custom_data",
        "service_id": 14,
        "customer_name": "easytransfert"
    }
}
```

### Exemple – transaction échouée

```json
{
    "status": "error",
    "message": "Transaction échouée",
    "data": {
        "transaction_id": "EFB.144359",
        "state": "FAILED",
        "reponse": "",
        "error": "Fonds insuffisants",
        "amount": 2000,
        "custom_data": "transaction_ref_123",
        "service_id": 10,
        "customer_name": "easytransfert"
    }
}
```

### Explication des champs spécifiques

| Champ | Type | Description |
|-------|------|-------------|
| `transaction_id` | String | Identifiant unique de la transaction |
| `state` | String | SUCCESS ou FAILED |
| `reponse` | String | Message de confirmation en cas de succès |
| `error` | String | Message d'erreur en cas d'échec |
| `amount` | Integer | Montant de la transaction |
| `custom_data` | String | Données personnalisées envoyées lors de l'initiation |
| `service_id` | Integer | Identifiant du service utilisé |
| `customer_name` | String | Nom du client / partenaire |

## Codes HTTP fréquents

| Code | Signification | Exemple de cas |
|------|---------------|----------------|
| **200** | OK | Requête reçue et traitée correctement |
| **400** | Bad Request | Paramètres manquants ou invalides (ex: amount manquant, JSON invalide) |
| **401** | Unauthorized | Clé API invalide ou manquante |
| **403** | Forbidden | Accès refusé, limite dépassée, service non autorisé |
| **404** | Not Found | Transaction ID inexistant lors de l'interrogation du statut |
| **429** | Too Many Requests | Trop de requêtes envoyées en peu de temps (rate limiting) |
| **500** | Internal Server Error | Erreur côté serveur EASYTRANSFERT |

<Info>
  Remarque : Même en cas d'erreur, la réponse est généralement au format JSON avec `status: "error"` et un message explicatif.
</Info>

## Exemples de réponses d'erreur

### Erreur 400 - Bad Request

```json
{
    "status": "error",
    "message": "Paramètre manquant : amount",
    "data": null
}
```

### Erreur 401 - Unauthorized

```json
{
    "status": "error",
    "message": "Clé API invalide ou manquante",
    "data": null
}
```

### Erreur 429 - Too Many Requests

```json
{
    "status": "error",
    "message": "Trop de requêtes. Veuillez réessayer plus tard.",
    "data": null
}
```

<Warning>
  En cas d'erreur 429, respectez le header `Retry-After` si fourni pour éviter un blocage temporaire.
</Warning>

## Traitement des réponses

### Réponse immédiate vs IPN

<CardGroup cols={2}>
  <Card title="Réponse immédiate" icon="bolt">
    Reçue immédiatement après l'appel API. Indique que la requête a été acceptée, mais **ne confirme pas** le succès final de la transaction.
  </Card>
  <Card title="IPN (source de vérité)" icon="webhook" color="#1d60d5">
    Reçue de manière asynchrone. Contient le statut final réel (SUCCESS ou FAILED) de la transaction.
  </Card>
</CardGroup>

### États possibles dans les réponses

| État | Description | Action recommandée |
|------|-------------|-------------------|
| **PENDING** | Transaction en cours de traitement | Attendre la notification IPN |
| **SUCCESS** | Transaction réussie | Traiter la transaction (créditer, notifier, etc.) |
| **FAILED** | Transaction échouée | Logger l'erreur et informer l'utilisateur |
| **CANCELLED** | Transaction annulée | Traiter comme un échec |

<Warning>
  **Important :** Ne jamais considérer la réponse immédiate comme définitive. Seule la notification IPN confirme le statut final de la transaction.
</Warning>

## Exemple de workflow complet

<Steps>
  <Step title="Envoyer la requête">
    POST /airtime avec tous les paramètres requis
  </Step>
  <Step title="Recevoir la réponse immédiate">
    Vérifier le code HTTP et le status. Enregistrer le transaction_id.
  </Step>
  <Step title="Attendre l'IPN">
    La notification IPN arrive de manière asynchrone avec le statut final.
  </Step>
  <Step title="Traiter selon le statut">
    SUCCESS : créditer, notifier. FAILED : logger, informer l'utilisateur.
  </Step>
</Steps>

<Tip>
  La structure uniforme des réponses facilite le traitement côté client et la gestion d'erreurs. Implémentez toujours une logique de traitement asynchrone basée sur les IPN.
</Tip>
